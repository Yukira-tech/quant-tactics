# TIMING.md — StrategyEngine 时序文档

## 一、系统时序总览

```
启动阶段：
  C++ 编译启动          ~1-2s
  Go 服务器启动         ~100ms
  YukiPilot 初始化      ~200ms（无训练）
  YukiPilot 训练（可选）~8-20s（CPU，依数据量）
  前端连接              ~500ms

运行阶段（每轮 tick）：
  C++ 因子计算          ~50-200ms（5000 只股票，并行）
  C++ 写运行时文件      ~10-50ms
  YukiPilot 读文件+推理 ~100-300ms
  YukiPilot 写决策文件  ~5-20ms
  Go 检测文件变化       ~1s（轮询间隔）
  Go 推送前端           ~10-50ms
  前端渲染              ~16ms（一帧）
```

---

## 二、关键路径分析

### 路径 1：C++ → 运行时文件

```
DataLoader 加载 → FactorEngine 计算 → StrategyEngine 信号
→ PositionManager 持仓 → DataWriter 写文件
```

**耗时估算**：5000 只股票，16 线程并行，约 200-500ms/轮。

**瓶颈**：

- 磁盘 I/O（读历史数据）
- 文件写入（需原子写，有 fsync 开销）

**优化方向**：

- 增量加载，减少重复读盘
- 批量写文件，减少 fsync 次数
- 内存映射文件（mmap）

**C++ 双入口影响**：

- `main_single.cpp` 单文件版，编译快，运行无区别
- `main_modular.cpp` 模块化版，链接阶段稍慢，运行性能一致
- 时序上两个入口等效

---

### 路径 2：YukiPilot 决策

```
读文件 → 特征构建 → Transformer 推理 → 规则融合 → 风控 → 写回
```

**耗时估算**：单标的约 20-50ms，100 标的串行约 2-5s。

**瓶颈**：

- 逐标的串行处理
- 文件读写
- Transformer 推理（CPU）

**优化方向**：

- 批量推理（多个标的合成一个 batch）
- 异步 IO
- 模型量化 / 导出 ONNX

**训练耗时**：

- 68K 参数，CPU 训练
- 1 票 × 60 根：约 2s
- 10 票 × 250 根：约 15-20s
- 50 票 × 500 根：约 1-2min

**流式进度开销**：

- batch 级进度条：每 batch 一次 stdout write + flush，无性能压力
- 训练进度文件写入：节流每 200ms 一次，可忽略

---

### 路径 3：Go → 前端

```
watcher 检测 → snapshot 构建 → WebSocket 推送 → 前端渲染
```

**耗时估算**：约 1-2s（含 watcher 轮询间隔 1s）。

**瓶颈**：

- watcher 轮询间隔固定 1s
- snapshot 构建需读取多个文件

**优化方向**：

- 使用 fsnotify 替代轮询
- snapshot 增量更新，只读变化的文件
- WebSocket 推送改为事件驱动

---

## 三、单轮全链路延迟

以 C++ 开始新轮计算到前端看到更新：

| 环节 | 耗时 | 累计 |
|------|------|------|
| C++ 计算 + 写文件 | 200-500ms | 500ms |
| YukiPilot 读取 + 决策 + 写回 | 2-5s | 5.5s |
| Go watcher 检测（轮询 1s） | 0-1s | 6.5s |
| Go snapshot 构建 | 50-100ms | 6.6s |
| WebSocket 推送 + 前端渲染 | 50ms | 6.65s |

**结论**：单轮全链路延迟约 **6-7 秒**，主要瓶颈在 YukiPilot 串行处理和 Go watcher 轮询间隔。

对于秒级刷新的监控需求，这个延迟可以接受。但如果未来要做分钟级甚至秒级交易，需要：

1. YukiPilot 批量推理 + 异步处理
2. Go 改用 fsnotify 实时监听
3. 减少文件读写次数，考虑共享内存或消息队列

## 四、训练时序

### 4.1 训练流水线

```
构建特征矩阵 → 滑窗切分 → 8:2 时序切分 → 训练 → 保存 checkpoint
```

### 4.2 CPU 训练耗时

| 数据规模 | 样本量 | 训练耗时（20 epochs） |
|----------|--------|----------------------|
| 1 票 × 60 根 | 24 | ~2s |
| 1 票 × 250 根 | 220 | ~5s |
| 10 票 × 250 根 | 2,200 | ~15-20s |
| 50 票 × 500 根 | 24,000 | ~1-2min |

### 4.3 训练进度输出

- batch 级单行进度条：16 格、loss、速度、ETA
- 速度用最近 50 个 batch 滑动平均
- 进度文件原子写：节流每 200ms 一次

### 4.4 训练回调时序

```
on_train_start(total_epochs, total_batches)
  ↓
on_batch_end(epoch, total_epochs, batch, total_batches, loss, eta)
  ↓
on_epoch_end(epoch_metrics)
  ↓
finish()
```

每个 epoch 结束强制写一次进度文件，供前端训练面板轮询展示。

## 五、LLM Agent 时序

### 5.1 单标的决策

| 阶段 | 耗时 |
|------|------|
| 工具调用 | 本地执行，通常 <10ms |
| LLM 响应 | 网络 + 推理，1-5s |
| 流式输出 | 逐 token 打字机，与响应同步 |
| 最大轮数 | 6 轮 |
| 墙钟超时 | 30 秒 |

### 5.2 降级时序

| 场景 | 行为 |
|------|------|
| 无 LLM / 无 API key | 立即降级规则模板 |
| LLM 超时 | 30 秒后返回 None，降级 |
| LLM 解析失败 | 立即降级 |
| 工具执行失败 | 返回错误 JSON，不中断循环 |

## 七、文件 IO 时序

### 7.1 原子写

```
写 tmp 文件 → fsync → rename 覆盖
```

**耗时**：约 1-5ms/文件（本地磁盘）。

**注意**：fsync 是性能杀手。如果文件系统不支持原子 rename，需要额外处理。

### 7.2 批量写

5000 只股票，每只写一个 JSON 文件：

**串行**：5-25 秒  
**并行**：1-5 秒（受磁盘带宽限制）

**建议**：MVP 阶段串行即可，后续优化为并行写或合并为单文件。

### 7.3 运行时文件动态创建

以下目录由程序运行时自动创建，初始目录树中不包含：

```
runtime_files/training/progress.json      # YukiPilot 训练进度
runtime_files/agent_thinking/{code}.json  # LLM 思考状态
```

## 八、性能优化路线图

| 优先级 | 优化项 | 预期收益 |
|--------|--------|----------|
| 高 | YukiPilot 批量推理 | 决策耗时降低 5-10 倍 |
| 高 | Go 改用 fsnotify | 检测延迟从 1s 降至毫秒级 |
| 中 | C++ 增量加载数据 | 启动时间大幅降低 |
| 中 | 文件写入合并批处理 | 减少 fsync 次数 |
| 低 | 模型量化/ONNX | CPU 推理提速 2-3 倍 |
| 低 | 共享内存替代文件通信 | 跨语言延迟降至微秒级 |

## 九、C++ 双入口时序说明

| 阶段 | main_single.cpp | main_modular.cpp |
|------|-----------------|------------------|
| 编译 | 单文件，最快 | 多个头文件，稍慢 |
| 启动 | 无链接依赖，最快 | 无显著差异 |
| 运行 | 与模块化版等效 | 与单文件版等效 |
| 增量编译 | 单文件变化需整体重编 | 只重编变化模块 |

当前阶段两个入口性能差异可忽略。未来以 `main_modular.cpp` 为唯一入口时，增量编译优势会更明显。
